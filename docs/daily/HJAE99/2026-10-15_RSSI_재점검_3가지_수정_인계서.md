## 2. remeasurement.py의 출처와 역할

`ros2_ws/src/scv_survey/scv_survey/remeasurement.py`는 **이번 재점검 수정 과정에서 새로 작성한 파일**이다. 받아온 통합 브랜치에서 가져온 파일이 아니다. 작성 주체는 이번 대화의 코드 작업 에이전트이며, 사용자가 직접 작성했던 기존 파일로 기록하지 않는다.

작성 전 확인한 Git 근거:

- 기준 HEAD `c0f7aed...`의 트리에 이 경로가 없다.
- 로컬 `origin/temp/integration-1014` 참조에도 이 경로가 없다.
- 첫 커밋 전 `git status`에서 `??`로 표시되는 새 파일이었다.
- 당시 로컬 Git 전체 이력에서 이 경로의 커밋 기록이 없었다. 다른 PC나 미수신 브랜치의 파일 존재까지 부정하는 근거는 아니다.

기존 재점검 기능 자체는 이미 있었다. `manager_core.remeasure_targets()`가 대상 칸을 고르고, `mission_executor.measure()`가 정밀측정을 요청하며, `precise_server`가 RSSI를 모으고, `inspection_manager.apply_remeasure()`가 결과를 반영했다. 이번 작업은 이 기존 흐름을 수정한 것이다.

새 파일은 두 가지 작은 로직을 분리한다.

| 구성 | 역할 | 사용하는 곳 |
| --- | --- | --- |
| `classify()` | 측정 유효성·최소 표본·평균값 유효성 검사 후 정상/약한 신호/미검출/판정 불가 반환 | `inspection_manager.remeasure_state()` |
| `MeasurementWindow` | 이번 정밀측정 시간 창 안의 새 스캔만 받고 검출·미검출을 집계 | `precise_server` |

실제 평균·비율 분류식은 기존 `heatmap.py`에 추가한 `rf_status()`를 공유한다. 기존 `CellStats`도 재사용한다. 새 ROS 노드나 DB 서버를 만든 파일이 아니므로 이 파일만 별도로 실행하거나 launch에 새 노드로 추가할 필요는 없다.

## 3. 용어와 계산 규칙

### 3.1 서로 다른 상황

| 이름 | 의미 | 대응 |
| --- | --- | --- |
| 미측정 | 해당 칸에 유효한 측정 시도 자료가 없음 | 별도 빈 칸 채우기 대상. 기본 RF 재점검 후보에서 제외 |
| 미검출 | 스캔 결과는 왔지만 대상 AP가 보이지 않음 | 미검출 횟수로 집계. 비율이 높으면 재점검 후보 |
| 약한 신호 | AP는 보였으나 검출 RSSI 평균이 기준 미만 | 재점검 후보 |
| 판정 불가 | 표본 부족, 수집 실패, 위치/정지 조건 실패 등으로 결론을 낼 수 없음 | 기존 자료 유지. 정상이나 이상 지속으로 확정하지 않음 |
| 재점검 | 위 후보를 다시 확인하는 행동 | 같은 섹터 로봇이 정지 측정 |

코드의 `shadow`는 약한 신호에 붙인 내부 분류명이다. **‘−72 미만’과 ‘음영’이 별개의 후보 기준인 것은 아니다.** 혼동을 줄이기 위해 1차에는 ‘약한 신호 후보’, 재점검 후에도 나쁘면 ‘이상 지속’으로 설명한다.

### 3.2 계산식과 현재 기본값

```text
n_detected = AP가 검출된 유효 스캔 수
n_missed   = AP가 미검출된 유효 스캔 수
n_total    = n_detected + n_missed
mean       = 검출된 RSSI 합 / n_detected  (검출 0개이면 평균 없음)
miss_ratio = n_missed / n_total          (전체 0개이면 판정하지 않음)
```

- 최소 전체 표본: **3개**. 검출과 미검출 모두 시도 1회로 센다.
- 약한 신호: **검출 산술평균 < −72 dBm**. 단일 표본 하나가 −73이라고 바로 후보로 정하지 않는다.
- 미검출 이상: **미검출 비율 ≥ 0.5**, 또는 충분한 시도에서 검출 0개.
- 정상: 평균 **≥ −72**이고 미검출 비율 **< 0.5**이며 측정 유효성과 최소 표본을 모두 충족.
- 정확히 −72는 평균 조건상 정상이다. 비율이 정확히 50%면 미검출 조건상 이상이다.
- 중앙값·IQR은 진단용으로 유지하지만 이번 정상/이상 판단 기준으로 사용하지 않는다.
- 기준선 대비 변화량을 비교하지 않는다.

현재 최소 표본은 코드 기본 3이며, RSSI 임계값은 관제 ROS 파라미터 `shadow_dbm`, 측정 시간은 로봇 PC 파라미터 `precise_duration_s`를 사용한다. DB 설정을 회차별로 읽어 모든 노드에 일괄 고정·전달하는 기능까지 완료된 것은 아니다.

### 3.3 ‘검출 1회·미검출 29회’ 예시

| 항목 | 값 |
| --- | --- |
| 검출값 | −60 dBm 1개 |
| 미검출 | 29회 |
| 전체 | 30회 |
| 검출 평균 | −60 dBm |
| 미검출 비율 | 29/30 = 약 96.7% |
| 판정 | 평균은 좋지만 대부분 미검출이므로 이상 지속 |

이전에는 검출값만 남아 −60 하나를 보고 정상으로 판단할 수 있었다. 현재는 미검출 비율을 함께 판단하므로 이상 의심을 취소하지 않는다. 30회는 설명용 예시다. 기본 15초 동안 얻는 실제 개수는 스캔·발행 주기에 따라 달라진다.

## 4. 수정 ① — 미검출 원본 표본 보존

### 4.1 원인

`ros_bridge.on_sample()`은 `not m.detected`이면 바로 반환했다. 따라서 ROS의 칸 집계가 미검출을 세더라도 웹/DB 원본에는 해당 스캔이 남지 않았다. DB `net_samples.rssi_dbm`도 NOT NULL이어서 ‘측정했지만 AP를 못 찾음’을 숫자 없이 저장할 수 없었다.

숫자 RSSI만 저장하는 구조였다는 것은 코드로 확인된다. 누가 어떤 의도로 이 구조를 택했는지는 코드만으로 단정하지 않는다. 미검출 비율이 판정 근거가 된 현재 요구에는 맞지 않아 수정했다.

### 4.2 변경 경로

```text
NetRaw → 기존 태거 → NetSample
                         ├─ cell_map_writer → 칸 통계
                         └─ ros_bridge → server_page.on_samples → net_samples
```

- `ros_bridge.py`: 도크 위 표본 제외는 유지하되, 미검출을 걸러내지 않는다. 검출 여부를 전달하고 미검출 RSSI는 `None`으로 넘긴다.
- `01_schema.sql`: `net_samples.detected BOOLEAN NOT NULL DEFAULT true` 추가, RSSI의 NOT NULL 제거. 검출이면 숫자 필수, 미검출이면 NULL이어야 하는 CHECK 제약 추가.
- `server_page.py`: `detected=false`는 RSSI NULL로 저장한다. 실시간 히트맵 캐시와 DB 복원 집계는 검출 숫자만 누적한다. 표본 조회에는 detected, 작업별 칸 통계에는 검출/미검출 수를 포함한다.
- `static/server/app.js`: 미검출 표본을 회색과 ‘AP 미검출’ 문구로 표시한다. RSSI가 없는 값이 강한 신호 색으로 표시되지 않게 처리하고, 작업 상세 지도 대표값을 평균으로 맞춘다.
- 기존 `(robot_id, run_id, seq)` 중복 방지 키를 유지한다.

기존 숫자 행은 검출값으로 유지한다. 과거 −100을 임의로 미검출로 바꾸지 않는다. 과거에 버린 미검출 표본은 복원하지 못한다.

### 4.3 확인한 것과 남은 한계

격리 PostgreSQL에서 미검출 NULL 저장, 검출 평균 유지, 중복 재입력 무시, 전부 미검출인 경우 숫자 히트맵 생성 방지, 실시간 캐시 갱신을 확인했다. 브리지 수신 콜백도 미검출을 보존하는지 시험했다.

이 수정은 **미검출 필터 때문에 잃던 자료를 보존하는 것**이다. 브리지 DB 저장 실패 시 원본 재전송, 고정 run_id의 실제 회차 연결, 디스크 버퍼 내구성까지 해결한 것은 아니다.

## 5. 수정 ② — 잘못된 정상 판단과 무표본 혼동 방지

### 5.1 이전 문제

기존 `precise_server`는 detected=true의 RSSI만 리스트에 넣었다. 결과의 `n_samples`는 검출 수였지만 관제는 이 값만 보고 판단했다.

- 한 번만 검출되어도 좋은 값이면 정상 취소가 가능했다.
- 메시지 0건과 전부 미검출은 둘 다 검출 리스트가 비어 같은 결과가 됐다.
- 기존 관제는 결과 필드가 비면 사람이 읽는 reason 문자열에서 중앙값/개수를 복원하기도 했다.

### 5.2 새 결과 계약

`PreciseMeasure.action`과 `ExecuteTask.action` 결과에 다음 필드를 추가했다.

| 필드 | 의미 |
| --- | --- |
| `rssi_mean` | 검출 RSSI 산술평균. 검출 0개이면 사용하지 않음 |
| `n_total` | 검출 + 미검출 시도 수 |
| `n_missed` | 미검출 시도 수 |
| `duration_s` | 실제 측정 경과 시간 |
| `measurement_valid` | 정밀측정 결과 유효 여부 |
| `measurement_reason` | 취소·표본 부족 등 사유 |

기존 `n_samples`는 **검출 수**로 유지한다. `rssi_median`, `rssi_iqr`도 남긴다. `mission_executor`가 정밀측정 결과를 ExecuteTask 결과로 전달하며, 관제는 reason에서 수치를 추측해 복원하지 않는다.

### 5.3 새 표본 시간 창

`MeasurementWindow.add()`는 다음 자료를 제외한다.

1. 자신의 robot_id와 다른 로봇의 표본.
2. 같은 측정 시각으로 이미 받은 중복 스캔.
3. 이번 측정 시작 전 또는 요청 시간 창 뒤에 찍힌 표본.
4. 현재 ROS 시각보다 미래이거나 수신 시점 기준 2초보다 오래된 표본.
5. detected=true인데 RSSI 범위 −127~0을 벗어난 표본.

검출이면 RSSI 리스트에 넣고, 미검출이면 `n_missed`를 증가시킨다. 정밀측정 서버는 동시 요청과 허용 범위 밖의 측정 시간도 거절한다.

### 5.4 정지 측정과 판정 불가

기존 30초 고정을 **기본 15초, 요청 허용 10~15초**로 변경했다. 로봇은 기존 목표 칸 중앙점까지 간 뒤 정지 명령을 내리고, 1초 정지 확인 후 측정한다. 측정 중에도 조건을 반복 검사하고 결과 반영 전 다시 확인한다.

| 조건 | 현재 검사 |
| --- | --- |
| 목표 | `target_ref=cell:ix,iy` 형식, 실제 위치가 해당 셀 안 |
| 위치 확실성 | AMCL 위치 존재, 위치 표준편차가 `pose_std_max` 이하(기본 0.15 m) |
| 지도 | 지도 원점을 가진 static_map 수신 |
| 이동량 | 측정 시작 위치에서 0.05 m 이내, 방향 차이 0.10 rad 이내 |
| 정지 | odom 수신 나이 1초 이내, 선속도 ≤0.02 m/s, 각속도 ≤0.05 rad/s |
| 배터리 | 기존 귀환 기준 `DOCK_PCT`(20%)보다 높음 |
| 표본 | 전체 유효 시도 ≥3, 검출 수 + 미검출 수 = 전체 수 |
| 결과 | 취소/실패가 아닌 유효 결과, 관제가 확인하는 경과 시간 범위 10~16초 |

요청은 최대 15초지만 실제 루프 종료 지연을 고려해 관제 결과 검사는 16초까지 허용한다. 위치가 불확실하거나 움직였으면 정상 확인으로 처리하지 않는다. 이 조건은 현재 메서드 기준이며 실제 로봇에서의 안정성·센서 갱신 빈도는 현장 시험 대상이다.

**무표본**이면 판정 불가로 실패 처리하고 원래 칸 자료를 유지한다. **전부 미검출**이어도 유효 시도 3개 이상과 정지·위치 조건을 만족했다면 미검출 이상으로 판단할 수 있다.

안 온 메시지는 미검출로 세지 않는다. 현재는 최소 개수 검사이며, 15초 동안 꾸준한 빈도로 수집됐는지 확인하는 별도 수집률 검사는 미구현이다.

### 5.5 미측정 칸 재방문과의 관계

기존 `remeasure_targets(include_unmeasured=True)` 옵션과 10/14 실제 미측정 칸 재방문 기록이 있다. 현재 manager 기본값은 false다. **미측정 재방문 코드가 전혀 없다는 이전 설명은 정정한다.** 다만 별도 N-8 빈 칸 채우기 단계가 완성됐다는 뜻은 아니다.

이번 작업은 미측정 옵션을 켜거나 빈 칸 채우기를 새로 구현하지 않았다. 중앙이 위험할 때 같은 셀 안의 안전한 대체 정지점을 선택하는 개선도 아직 제안 단계다. 셀 내부 이동 측정은 추가하지 않았다.

## 6. 수정 ③ — 저장 성공 후 판정·작업 완료

### 6.1 이전 문제

기존 `on_task_result()`는 재점검 결과를 저장하기 전에 작업을 성공으로 끝냈다. `apply_remeasure()`는 저장 함수가 False를 반환한 것을 확인하지 않았고, DB 예외를 기록한 뒤에도 정상/이상 알림을 발행할 수 있었다.

또한 File 저장소는 표본 0개를 low 신뢰도로 보지만 DB 갱신은 무조건 ok로 저장했다. 새 결과를 반영하면서 이전 평균·분산·최솟값·최댓값이 남아 서로 다른 측정 결과가 섞일 수도 있었다.

### 6.2 변경 순서

```text
재점검 액션 결과 수신
  → 액션 성공 여부·측정 유효성 검사
  → 평균/미검출 비율로 판정
  → 해당 칸 저장 시도
      ├─ 성공: 정상/이상 알림 → 작업 완료 → 기존 다음 단계 진행
      └─ 실패: 결과 보관 → 작업 완료 보류 → 저장 재시도
```

- `apply_remeasure()`는 저장 성공 여부를 bool로 반환한다.
- DB RuntimeError, 파일 OSError 또는 저장 False이면 정상/이상 알림을 내지 않는다.
- 미저장 결과는 `pending_remeasure_results`에 두고 기존 dispatch 주기(0.5초)에서 재시도한다. 이 대기가 남아 있으면 dispatch에서 다음 작업 진행을 보류한다.
- 저장 성공 후에만 작업을 성공으로 닫는다. 이미 취소/종료된 작업의 보류 결과는 적용하지 않는다.
- 측정 자체가 판정 불가이면 저장 재시도 대상으로 정상 위장하지 않고 UNCONFIRMED/실패로 처리한다.

### 6.3 칸 통계와 회피 처리

- File/DB 모두 전체 표본 최소 3개를 기준으로 confidence를 ok/low로 정한다.
- `grid_stats`에 nullable `n_detected`, `n_missed`를 추가했다. 과거 자료에서 알 수 없는 횟수를 임의로 0으로 복원하지 않는다.
- 재점검 시 n(전체), 검출/미검출 수, 평균, 중앙값, 상태를 함께 갱신한다.
- 새 요약에 없는 분산·최솟값·최댓값은 NULL로 비워 이전 측정과 섞이지 않게 한다. DB의 기존 보간/기준선 변화량 표시도 갱신 시 해제한다.
- File 저장소는 요청 회차와 다른 문서를 읽거나 갱신하지 않도록 검사한다.
- 회피 마스크는 이번 재점검의 유효한 이상 결과가 **저장된 칸**만 대상으로 한다. 기존 Dock 보호 반경(기본 0.6 m)과 confidence 조건은 유지하므로 이상 칸 전체가 예외 없이 막히는 것은 아니다.

보완으로 자동 후보 수 기본 5개 제한을 0(전체)으로 바꿨고, 평균이 낮은 순으로 약한 신호 후보를 정렬한다. 양수 제한을 명시하면 그 제한은 유지한다. 표본 부족을 진짜 미측정으로 바꾸어 취급하지 않으며, 미재점검 칸을 이번 결과의 확정 회피 칸으로 취급하지 않는다.

### 6.4 남은 한계

보류 결과와 확정 회피 셀 집합은 **메모리 상태**다. 프로세스 재시작 후 복구하는 디스크 아웃박스가 아니다. DB 오류가 계속되면 진행이 보류되며, 운영 중 문제 해결과 재시작 복구 정책은 추가 구현 대상이다. DB 칸 요약 저장 성공이 후보/정밀측정/이상 이력 테이블 전체의 한 트랜잭션 완료를 뜻하지도 않는다.

## 8. 전달받은 사람이 적용할 순서

1. 이 변경 브랜치의 메시지·관제·측정·주행 파일을 함께 받는다. 새 결과 필드가 있으므로 파일 한두 개만 복사해서 기존 설치와 섞지 않는다.
2. 별도 시험 DB에서 변경된 `ros2_ws/scv_db/sql/01_schema.sql`을 적용한다. 신규 DB는 기존 절차대로 01 다음 02를 적용한다. 운영 DB 반영은 담당자가 적용 범위를 확인한 뒤 수행한다.
3. 스키마 적용 시 기존 `precise_duration_s=30` 설정만 15로 이전한다. 이미 10~15로 조정한 값은 유지한다. 다른 사용자 지정값까지 자동으로 유효하게 만드는 것은 아니다.
4. 관제 PC·로봇 PC의 `scv_msgs` 및 의존 패키지를 함께 재빌드하고 새 환경을 source한다. 정밀측정 서버와 mission_executor가 같은 인터페이스를 사용해야 한다.
5. 로봇 PC의 `precise_duration_s`를 10~15로 맞추고, 셀 크기·지도 원점·담당 섹터가 실제 지도와 같은지 확인한다. DB 설정만 바꿨다고 ROS 파라미터까지 자동 변경된다고 가정하지 않는다.
6. 관련 확인 시험을 먼저 수행한다. DB 시험은 **격리 DB의 DSN**을 `SCV_RSSI_TEST_DSN`으로 명시해야 한다. ROS 액션 시험은 자체적으로 domain191/localhost를 설정하고 주행 노드를 사용하지 않는다.
7. 실제 이동 시험은 알맞은 PC와 담당자 승인하에 진행한다. 정상 확인, 이상 지속, 스캐너 메시지 없음, 전부 미검출, 위치/정지 실패, DB 중단·복구를 서로 다른 시나리오로 확인한다.

ROS 환경과 변경 메시지를 빌드/source한 뒤 실행하는 로직 확인 예시(저장소 루트):

```bash
PYTHONPATH="$PWD/ros2_ws/src/scv_survey:$PWD/ros2_ws/src/scv_manager:$PYTHONPATH" \
python3 -m pytest -q \
  ros2_ws/src/scv_survey/test/test_remeasurement.py \
  ros2_ws/src/scv_survey/test/test_cellmap_store.py \
  ros2_ws/src/scv_manager/test/test_remeasure_result.py \
  ros2_ws/src/scv_nav/test/test_measurement_guard.py
```

실제 주행 확인에서는 정지 전후 위치·odom 속도, 요청 시간/실제 시간, 검출/미검출/전체 수, 평균, 작업 결과, DB 저장 결과, 발행된 회피 셀을 함께 남긴다. 수신 메시지 개수는 스캔 주기에 따라 달라지므로 15초=정확히 15개라고 고정해서 판정하지 않는다.

## 9. 전체 통합에서 남은 일

이번 세 결함 수정과 아래 작업의 완료 여부를 구분해야 한다.

- DB settings를 회차 시작에 고정하고 관련 노드에 일관되게 전달.
- TF 태거의 실제 run_id와 표본 고유 키 전달, 원본 재전송·디스크 내구성.
- `precise_measures / candidates / findings` 및 `REMAINS`와 DB 상태의 일관된 이력 연결.
- 프로세스 재시작 후 미저장 결과·회피 상태 복구.
- 최초 칸 맵 commit 실패/타임아웃 및 DB 읽기 실패 시 다음 단계 진행 정책 보완.
- 별도 미측정 칸 채우기(N-8), 외부 후보의 섹터 검증, 안전 대체 정지점 선택.
- 최소 표본을 넘어선 측정 수집률 기준과 실제 로봇 시험.

전체 실행 계획은 [`docs/control/RSSI_REINSPECTION_PLAN.md`](../../control/RSSI_REINSPECTION_PLAN.md), 메시지 변경 기록은 [`docs/interfaces.md`](../../interfaces.md)를 참고한다.
