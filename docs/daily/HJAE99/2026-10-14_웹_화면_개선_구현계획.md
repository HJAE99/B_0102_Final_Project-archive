## 1. 목표와 작업 범위

지도 한 화면에서 **로봇이 어디에 있고, 무엇을 점검하며, 어디에 문제가 있는지** 알아볼 수 있게 만든다. 메인 지도에 현재 회차 히트맵을 연결하고, 연속 색상과 제한된 보간으로 자연스럽게 표시한다. 개발용 격자·번호·좌표는 기본 화면에서 숨긴다.

이번 작업은 **웹이 값을 받아오는 방식의 정리와 웹에 표시하는 방식의 개선을 함께 포함한다.** 기존 설정에 있는 값은 다시 입력하지 않고 읽어오며, ROS/DB에 있는 정보를 웹에 연결한다. 데이터 연결을 뒤로 미루고 외형만 먼저 완성하는 계획으로 진행하지 않는다.

필요한 수정 범위는 공통 설정 읽기, 읽기 전용 ROS 연결, API 응답 정리, 웹 표시·갱신이다. ROS 주행 알고리즘·waypoint 생성·원본 저장/sync·DB 회차 소유권은 다시 설계하지 않는다. 미수신 정보를 정상값으로 채우거나 웹이 임의로 초기 위치를 발행하는 흐름은 만들지 않는다.

- 실제 브라우저 화면을 직접 관찰한 결과가 아니라, 현재 렌더링 코드와 API를 읽고 작성한 제안이다.
- 기본 화면은 실시간 관제, 완료 회차는 결과 화면, 등록·수정은 설정 화면으로 구분한다.
- React/HTM·Leaflet·FastAPI를 유지한다. 새 웹 프레임워크나 지도 엔진을 도입하지 않는다.
- 현재 지도·격자·샘플·검사 이력을 삭제하지 않는다. 표시 간소화와 데이터 삭제를 구분한다.

### 1.1 이번 사용자 요구로 정리한 원칙

1. 로봇 시작점은 이미 정해져 있으므로 웹에서 중복 입력하지 않고 원본 설정을 읽는다.
2. 시작점, 실시간 위치, 실제 Dock 위치, Dock 접근 자세는 의미가 다르므로 구분한다.
3. 웹에 읽어온 정보가 모두 지도에 그려져야 하는 것은 아니다. 목적에 맞는 정보만 표시한다.
4. 실제 로봇 지도/RViz의 표현을 웹에 그대로 복제하지 않는다. 웹용 색·아이콘·요약·표시 레이어를 사용한다.
5. 전체 작업을 단계별로 순서대로 진행한다. 단계마다 변경 범위만 검증하고, 마지막에 종합 검증한다. 사용자에게 매 단계 진행 승인을 다시 요구하지 않는다.

### 1.2 로봇 시작점과 현재 위치: 코드로 확인한 사실

`ros2_ws/src/scv_nav/scripts/mission_executor.py`의 HOME에 기본 시작 참고 자세가 있다. 이는 **undock 직후의 지도 좌표**이며, 현재 Dock 안에 있는 로봇의 실측 위치와 동일하다는 뜻은 아니다.

| 로봇 | 기본 시작 참고 x(m) | y(m) | 방향(도) |
| --- | ---: | ---: | ---: |
| robot3 | 2.806 | 4.610 | 179.9 |
| robot4 | 2.863 | 0.948 | 175.8 |

- 시작 시 x/y/yaw 파라미터를 모두 지정하면 HOME 대신 그 값이 사용된다. 실제 적용 설정을 확인할 수 있으면 우선 사용하고, 기본값만 읽었다면 기본 참고값이라고 표시한다.
- HOME 방향은 도 단위이며 웹 지도·RobotStatus.yaw는 라디안이다. 변환은 한 곳에서 수행한다.
- 현재 위치는 AMCL을 받은 주 ROS 실행기가 RobotStatus.x/y/yaw/pose_ok로 발행한다. 웹은 이를 읽어 실제 위치로 표시한다.
- 현재 웹 client는 DB의 dock_pose를 별도로 받아 initialpose를 발행할 수 있다. ROS 통합용 웹의 표시 기능은 이 동작을 재사용하지 않는다.
- `zones.yaml`의 dock는 실제 Dock 위치를 설명한다. HOME 또는 DB의 도크 접근 자세와 자동으로 같다고 처리하지 않는다.

표시 규칙: 시작 참고점은 작은 기준 아이콘으로 선택 표시하고, 유효한 최신 위치가 오면 현재 로봇 마커를 표시한다. 위치를 받지 못했다면 시작점에 실제 로봇이 있다고 단정하지 않는다. pose_ok=false일 때의 기본 (0,0)을 실제 위치로 그리지 않는다. 연결이 끊기면 마지막 유효 위치와 마지막 수신 시각을 표시한다.

## 2. 먼저 상정하는 목표 화면

```text
┌─────────────────────────────────────────────────────────┐
│ SCV 관제 · 현재 회차 · 연결 상태 · 최근 갱신               │
├──────────────────────────────────────┬──────────────────┤
│                                      │ 로봇 3 / 로봇 4  │
│             지도 + 히트맵            │ 위치 수신·상태   │
│                                      ├──────────────────┤
│ 로봇 위치 / 이상 설비 / 선택한 경로    │ 선택 대상 상세   │
│                                      │ 측정값·결과·사진 │
│ [히트맵] [경로] [구역] [측정점]       │                  │
│            신호 색상 범례             │                  │
├──────────────────────────────────────┴──────────────────┤
│ 중요 경보 · 최근 이벤트                    [전체 기록]   │
└─────────────────────────────────────────────────────────┘
```

지도와 히트맵을 중심에 두고 로봇 상태는 오른쪽에 고정한다. 설비·로봇·측정 위치를 선택하면 같은 상세 패널의 내용만 바뀐다. 긴 로그·좌표 표·모든 작업 목록은 기본 화면을 밀어내지 않고 상세 화면에서 본다.

이 배치는 화면 제안이며 모든 정보를 상시 노출하겠다는 뜻이 아니다. 오른쪽 로봇 카드는 실제 수신한 위치/상태/작업/배터리를 요약하고, 시작 참고값·원본 좌표·진단 수치는 상세에서 확인한다. 배터리와 작업 값도 웹에서 넣는 예시값이 아니라 원본을 읽어 표시한다.

기본 표시: 기준 지도, 현재 회차 히트맵, 로봇, 설비 아이콘, 중요 경보. 선택 표시: 현재 작업 경로, 구역 경계, 측정점. 분석 모드: 격자 테두리·칸 번호·좌표·관측 자세.

| 레이어 갱신 | 결과 변경 시 overlay 전체를 비우고 다시 그림 | 히트맵·설비·경로·선택 강조를 독립 갱신 |
| 정보 화면 | DB 표 이름·행 수·내부 필드를 드러내는 관리 화면 | 운영자는 등록 항목 중심, 원본 DB 표는 고급 관리로 이동 |

유지할 부분도 있다. 현재 로봇 마커는 새로 지도를 만들지 않고 위치만 갱신한다. 지도 좌표에 Leaflet CRS.Simple을 사용한 것도 유지할 수 있다. 전체 웹을 새로 만드는 방식으로 진행하지 않는다.

## 4. 맵을 웹에 표시하는 방식: 현재와 권장안

### 4.1 현재는 무엇을 불러오는가

현재 웹 메인 지도는 ROS `/map`을 직접 구독하지 않는다. 다음 경로를 사용한다.

```text
YAML + PGM을 웹에 업로드
  → server_page.upload_map: YAML에서 해상도·원점 읽기, PGM을 PNG로 변환
  → maps에 메타데이터, scv_media/maps에 PNG 저장
  → GET /api/maps/active: 이미지 URL·크기·원점·격자·등록 정보 반환
  → MapView: Leaflet CRS.Simple + imageOverlay로 지도 표시
  → 같은 좌표계에 로봇·격자·설비를 추가
```

**지도 이미지를 웹에 올리고 그 위에 마커를 겹치는 방식 자체는 적절하다.** Leaflet 공식 문서도 비지리적 좌표계에 CRS.Simple과 ImageOverlay를 사용한다. 현재 개선 대상은 수동 등록 과정, 정보의 과도한 노출, 히트맵 연결과 표시 레이어의 구성이다.

PGM을 그대로 브라우저에 보내는 대신 PNG로 바꾸는 것은 웹에서 읽을 수 있게 하는 표현 변환이다. 예쁘게 보이도록 지도 엔진을 교체하거나 다른 지도 모양을 임의로 만들 필요는 없다.

### 4.2 일반적인 두 가지 취득 방식

| 방식 | 데이터 취득과 웹 표시 | 장점 | 필요한 조건 |
| --- | --- | --- | --- |
| 정적 기준 지도 | 기준 YAML/PGM을 서버가 읽어 이미지+메타데이터로 제공 | 고정된 실내 지도에 단순하고 효율적. 현재 Leaflet 코드 재사용 | 서버가 읽을 기준 파일·로봇 배포 지도·DB 지도 일치 |
| ROS 지도 연결 | 연결 계층이 nav_msgs/OccupancyGrid를 받아 이미지 또는 Canvas 데이터로 변환 | ROS가 실제 사용하는 지도와 변경 시점 연동 가능 | ROS 연결 계층, 지도 식별·버전·좌표 처리, 변경 시 재렌더링 |

**첫 구현은 정적 기준 지도의 표시 방식을 유지하는 것을 권장한다.** 기준 지도 자동 읽기/등록을 별도 작업으로 추가할 수 있고, 수동 업로드는 다른 지도를 등록하는 관리자 기능으로 남길 수 있다. ROS `/map` 실시간 취득은 지도 변경을 따라갈 필요가 있을 때 추가한다.

지도는 매초 전체 전송하지 않는다. 지도/버전이 바뀔 때 기반 이미지를 바꾸고, 로봇·히트맵·결과를 별도로 갱신한다. 큰 지도에서만 타일 분할을 검토하며, 현재 실내 지도에 타일 서버·3D 엔진을 먼저 도입하지 않는다.

### 4.3 취득과 렌더링의 분리

```text
지도 취득: 기준 파일 또는 ROS 지도
  → 공통 지도 정보: map_id, 이미지, 원점, 해상도, 크기, 버전
  → 기본 지도 레이어

DB 측정 결과 → 히트맵 레이어
로봇 상태     → 로봇 레이어
설비·판정     → 설비 레이어
현재 작업     → 경로 레이어
사용자 선택   → 강조·상세 패널
```

브라우저는 파일 경로나 ROS 토픽을 직접 찾아다니지 않고, 서버가 정리한 데이터로 그린다. 지도 원본을 바꾸지 않고 표현만 다듬는다. 벽은 차분한 어두운 회색, 통로는 밝게, 미탐색 공간은 구분되는 회색으로 표시할 수 있다. 이때 원본의 벽·통로·미탐색 분류는 유지한다.

웹은 RViz의 모든 표시를 따라 그리지 않는다. costmap·LiDAR 점·TF 프레임·모든 waypoint·칸 ID·공분산 숫자처럼 운용 화면에 불필요한 것은 읽기/분석에 필요하더라도 기본 표시에서 제외한다. 설비·AP 이름은 선택 시 표시하고, 점검 결과는 운영자가 이해하는 아이콘과 문구로 표현한다.

바꿀 수 있는 것은 표시 항목·색·선·아이콘·라벨·배치다. 실제 위치와 히트맵을 겹치는 지도는 원점·축척·공간 관계를 유지한다. 별도의 배치도나 흐름도처럼 공간 관계를 바꾼 화면을 추가한다면 '개략도'로 구분하고 실측 지도처럼 사용하지 않는다.

### 4.4 좌표와 지도 일치 조건

- 이미지 너비 W, 높이 H, 해상도 r, 원점 (ox, oy)라면 지도 범위는 x=ox…ox+W×r, y=oy…oy+H×r이다.
- 이미지 좌표는 위에서 아래로, 지도 y는 아래에서 위로 증가하므로 y 방향을 맞춘다. Leaflet 좌표 순서는 [y, x]이다.
- 모든 레이어에 같은 변환 함수를 사용한다. 화면에 맞춘다고 지도를 늘이거나 히트맵만 별도 비율로 확대하지 않는다.
- 회차의 map_id가 현재 표시 지도와 다르면 히트맵을 겹치지 않는다. 적절한 지도를 선택하도록 안내한다.
- 현재 업로드는 origin yaw=0, negate=0만 지원한다. 회전된 지도를 지원한다고 가정하지 않는다. 회전 지원은 별도 변환 구현 뒤 추가한다.
- 지도 파일·DB 격자·ROS 좌표계가 일치해야 한다. 보기 좋은 지도도 좌표가 틀리면 사용할 수 없다.

## 5. 이 브랜치에서 이미 되는 것과 남은 연결

### 5.1 데이터별 읽기 원본과 변경 대상

| 데이터 | 현재 읽는 곳/문제 | 구현 시 읽을 원본과 규칙 |
| --- | --- | --- |
| 로봇 ID·시작 참고 자세 | 웹 DB 등록과 ROS HOME이 별도 | 시작 설정을 공통 읽기 설정으로 정리. 방향 단위·지도 식별·출처 명시 |
| 지도 해상도·원점·이미지 | 웹 업로드 YAML/PGM→DB/PNG | 기준 지도 파일에서 자동 취득 가능하게 보완. 업로드는 관리자용 유지 |
| 격자 크기 | 웹 기본 1.0m, ROS 기본 0.5m | 측정 원본 설정과 DB를 대조해 읽음. 웹에서 별도 기본값으로 계산하지 않음 |
| 구역·배정 로봇 | 웹 좌우 분할과 ROS 상하 구역이 다름 | ROS zones.yaml의 구역/배정을 기준으로 읽음. 웹 표시용 경계는 선택 표시 |
| 도크 위치·접근 자세 | 웹 DB dock_pose와 다른 ROS 기준값 혼재 | 실제 Dock 위치와 접근/시작 참고값을 서로 다른 필드로 제공 |
| 현재 위치·방향·위치 유효성 | /ws/ui는 웹 client 보고에 의존 | ROS RobotStatus의 x/y/yaw/pose_ok·stamp를 읽어 전달 |
| 작업·회차·배터리·경고 | 웹 client 상태와 ROS 상태가 별도 | ROS 상태를 웹 형식으로 적응. battery_percent/battery_pct 등 이름 변환 |
| 회차 이력·측정값·칸 판정 | DB에 저장, 일부 API는 평균만 반환 | runs/net_samples/grid_stats에서 읽음. 원본 측정과 판정을 구분 |
| 측정 AP | 웹 DB와 ROS 실행 인자가 별도 | 실제 측정 대상과 DB 등록값을 대조. SSID/AP 선택 의미를 유지 |
| 설비 등록·사진·판정 | DB와 ROS 설비 파일 중복, 결과 연결 일부 미완료 | 등록 원본과 결과를 별도로 읽음. 미등록/미수신은 그대로 표시 |

고정 정보는 공통 설정, 실시간 정보는 ROS, 누적/회차 결과는 DB를 기본 읽기 원본으로 잡는다. 기존 DB가 원본인 등록 데이터까지 전부 YAML로 옮기지는 않는다. 서로 다르게 저장된 값은 자동으로 덮어쓰지 않고 차이를 확인하도록 한다.

### 5.2 이미 구현된 기능과 연결 의존성

| 구분 | 확인된 상태 | 화면 개선에서의 처리 |
| --- | --- | --- |
| 원본 DB 저장·자동 sync | PLAN 12·13번 코드와 로봇 없는 검증이 들어 있음 | 다시 구현하지 않음 |
| ROS 회차 소유 | SCV_RUN_OWNER=ros 선택 모드 존재 | 모드를 UI에 전달해 웹 자체 순찰 버튼 노출을 구분 |
| 외부 DB 저장 반영 | ros 모드는 live_cells 캐시 대신 재집계, 미검출 제외 | 기존 연결을 활용. DB 데이터가 실제 있어야 표시 가능 |
| 히트맵 API | /api/runs/{run_id}가 칸/AP별 평균값·표본 수 반환 | 1차 메인 연결에 활용하고 평균값임을 표시 |
| 최종 칸 판정 | ROS가 grid_stats에 저장. 기존 heat API와 기준이 다름 | 최종 표현용 응답에 중앙값·state·confidence를 보완 |
| 로봇 실시간 상태 | /ws/ui는 기존 웹 agent의 메모리 상태를 사용 | ROS 모드의 로봇 상태 전달은 별도 연결 필요 |
| ROS 알림·설비 결과·사진 | ros_bridge와 tasks/inspections 등 연결은 미완료 | 수신되지 않은 값은 대기/미수신 표시. 정상값을 만들어 채우지 않음 |

ROS 모드에서는 웹 agent 연결을 차단하므로, DB 히트맵이 연결됐다는 사실만으로 로봇 위치·상태도 웹에 연결됐다고 볼 수 없다. **읽기 전용 ROS 상태 연결을 독립적인 초기 구현 단계로 올린다.** 표시 카드만 먼저 만들고 상태 연결을 마지막에 남기는 방식은 피한다.

S2에서는 값의 수신 여부도 전달한다. 주 ROS 실행기는 배터리의 초기 기본값이 100이므로, 실제 센서 수신 여부를 확인하지 않은 값을 실측 100%로 표시하지 않는다. 위치 유효성과 데이터 갱신 시각도 함께 전달한다. 읽기 전용 연결을 위해 기존 웹 client를 실행해 초기 위치/주행 동작이 함께 켜지게 하지 않는다.

## 6. 히트맵 표현 규칙

### 6.1 값과 색

- 운영 화면은 실제 판정과 맞는 중앙값·칸 상태를 최종 기준으로 사용한다. 1차 연결에서 기존 평균값 API를 사용하면 범례와 상세에 평균이라고 명시한다.
- 측정 대상 AP를 명확히 선택하고 표시한다. 여러 AP의 가장 센 값만 섞어 특정 AP의 음영이 가려지지 않게 한다.
- 약한 신호는 코랄, 중간은 주황·연노랑, 강한 신호는 청록으로 이어지는 연속 색상 사용을 제안한다.
- 예시 표시 범위는 -90…-40 dBm이며 실제 자료로 확정한다. 회차/화면마다 범위를 자동으로 바꾸지 않는다. 음영 기준값은 실제 설정에서 읽는다.
- 불투명도는 우선 약 40%에서 검토하고 조절 기능을 둔다. 벽·통로·로봇이 계속 읽혀야 한다.
- 값이 없는 영역, 미검출, 검출됐으나 약한 신호를 구분한다. 범례에 색과 의미를 함께 표시한다.

### 6.2 공간 보간

추천 시작점은 **주변 네 칸의 유효 측정값을 사용하는 쌍선형 보간**이다. 각 방향의 거리 비율로 값을 이어 주는 방식이며, 이웃값의 범위를 벗어나는 과장된 피크를 만들지 않는다.

- 주변 값이 부족한 곳은 억지로 채우지 않고 원본 칸/미측정으로 표시한다. 먼 측정점을 가져와 빈 영역 전체를 메우지 않는다.
- 미검출의 0 dBm을 유효 신호로 보간하지 않는다. 미검출은 별도 상태 표시로 남긴다.
- 벽을 사이에 둔 측정값은 함께 보간하지 않는다. 벽 색만 지우는 후처리로는 벽 너머 신호 섞임을 해결할 수 없다.
- 지도 밖·벽·미탐색 영역을 마스크 처리하고, 측정량/신뢰도가 부족한 범위는 표시를 약하게 하거나 보간에서 제외한다.
- 보간값은 화면용 추정값이다. DB 원본, 음영 확정, 재측정/회피 판단에 다시 넣지 않는다.
- '부드러운 보기 / 측정 칸 보기' 전환 제공. 상세에는 실제 측정값과 추정값을 구분한다.

예: 벽이 없는 같은 공간의 -50과 -70 dBm 사이를 선형으로 이으면 중간은 -60 dBm이다. 중간에서 실제로 -60을 측정했다는 뜻은 아니다. 표본 조건이 충족된 범위에서만 이런 표현을 적용한다.

## 7. 화면 상태·갱신·상호작용

- 지도 메타데이터, 현재 회차, 로봇 상태, 히트맵, 선택 대상, 표시 레이어를 공통 화면 상태에서 관리한다.
- 정적 지도 정보는 진입/지도 변경 시, 로봇 상태는 기존 1Hz 수신을 활용, 히트맵은 2~3초 갱신부터 시작한다. 모든 데이터를 같은 주기로 읽지 않는다.
- 완료 회차는 반복 조회를 중단하고, 화면을 떠나면 조회 타이머와 구독을 정리한다. 회차가 바뀐 뒤 늦게 도착한 이전 응답은 버린다.
- 현재 run을 따라보는 모드와 특정 과거 run을 고정해서 보는 모드를 구분한다.
- '웹 연결됨', '로봇 응답 있음', '새 측정값 수신됨'은 서로 다른 상태다. 연결만 됐다고 전체를 정상/실시간으로 표시하지 않는다.
- 로봇 대표 상태는 작업 중·대기·복귀·막힘·비상정지·오프라인으로 구분한다. 원본이 없으면 미수신으로 표시한다.
- 로봇/설비/측정 위치를 선택하면 오른쪽 상세 갱신, 배경 선택은 해제. 상세 내용이 길어도 지도 크기는 유지한다.
- 확대·이동·레이어 선택은 데이터 갱신 때 유지한다. 지도 전체 맞춤은 처음 로드와 사용자의 '전체 보기' 요청에 적용한다.
- 긴 로그 대신 중요 경보와 최근 이벤트를 보여주고 전체 기록은 펼치기/결과 화면으로 이동한다.
- 실제 데이터가 없는 미리보기는 '샘플 데이터'라고 표시한다. 실제 계측·실제 로봇 연결 성공으로 기록하지 않는다.

## 8. 구현 플랜과 단계별 완료 기준

순서는 **고정 기본 정보 자동 읽기 → 실시간 정보 읽기 → DB 측정/결과 연결 → 화면 배치/표시 정리 → 색/보간 → 현장 연결 검증**이다. 이번 사용자 요구에 맞춰 데이터 수신을 앞 단계로 옮겼다. 한 번에 API·주행·DB·웹을 모두 바꾸지 않는다.

| 단계 | 작업 | 변경 중심 | 완료 기준 |
| --- | --- | --- | --- |
| S0 | 현재 원본·중복 흐름·범위 검토 | HOME, 상태 메시지, 웹 API, 본 계획 | 이번 프롬프트까지 검토 완료. 코드 구현 완료를 뜻하지 않음 |
| S1 | 고정 기본 정보 자동 읽기: 시작 참고 자세·지도 정보·모드·출처 | 공통 설정 읽기, 기존 지도 API 보완, 최소 표시 | 웹에 같은 시작값을 다시 입력하지 않음. 참고점과 실제 위치가 구분됨 |
| S2 | 읽기 전용 ROS 상태·위치·배터리·알림 연결 | 연결 계층, 메시지 변환, 서버 상태 응답 | 실측 수신/미수신/위치 불확실/오프라인을 구분. 웹 접속으로 초기 위치나 motion을 발행하지 않음 |
| S3 | 현재 회차·AP·히트맵·칸 판정·결과 읽기 연결 | 기존 DB/API, 화면 공통 상태 | 실제 DB 값과 화면 값 일치. 평균/중앙값 구분. 회차·지도 혼입 없음 |
| S4 | 지도 중심 배치·선택 상세·경보·필요 정보만 표시, 레이어 분리 | MonitorPage, MapView, app.css | RViz/DB 모든 항목을 복제하지 않음. 격자·내부 ID 기본 숨김. 선택/확대 상태 유지 |
| S5 | 연속 색·범례·반투명 Canvas·제한된 보간·원본 보기 | 색/보간 도우미, 히트맵 레이어 | 미검출·미측정·벽 너머를 채우지 않음. 실제 값과 추정값 구분 |
| S6 | 결과/설정 간소화·응답성·실제 연결·끊김 검증 | 각 화면, 실제 PC 연결 | 구현된 데이터별로 실제 수신 결과 기록. 빠진 연결은 남은 일로 명시 |

**S1부터 S6까지 순차 구현·검증했다.** 실제 장비가 필요한 운용 검증은 별도 대기 항목이다. 다른 단계를 동시에 구현하거나 전체 화면을 한 번에 교체하지 않는다. S2·S3에서는 해당 값 확인에 필요한 최소 표시만 사용하고, 전체 디자인 정리는 S4에서 한다.

단계별로 원본/응답 확인, 해당 화면 확인, 실패/미수신 확인, 변경 파일·검증 결과 정리를 마친다. 실제 수신이 필요한 검증과 가짜 메시지 검증은 구분해서 기록한다.

### 8.1 첫 작업 S1: 착수 범위

목표는 **기존에 정해진 로봇·지도 기본 정보를 웹이 읽어 사용하게 만드는 것**이다. 첫 단계에서 히트맵 보간이나 전체 CSS 교체까지 하지 않는다.

1. HOME의 로봇별 기본 시작 참고값을 공통 읽기 설정으로 정리한다. 웹에서 숫자를 다시 하드코딩하거나 전체 mission_executor 모듈을 import해 ROS 실행 의존성을 끌어오지 않는다.
2. ROS 실행기도 같은 기본 설정을 사용하도록 필요한 설정 읽기만 조정한다. 기존 숫자·각도 단위·x/y/yaw 전체 지정 시 우선 적용하는 규칙은 유지한다. 주행/초기화 알고리즘은 변경하지 않는다.
3. 기존 지도 응답에 시작 참고 자세·값의 출처·지도 일치 여부·run_owner를 필요한 최소 필드로 제공한다. 해상도·원점은 이미 읽고 있으므로 같은 기능을 중복 구현하지 않는다.
4. 웹에 시작 참고점과 '현재 위치 미수신'을 구분해서 표시한다. 기본 설정과 실제 적용 설정이 다를 수 있으면 확인되지 않은 실제 설정으로 표시하지 않는다.
5. 지도/설정 없음·지도 불일치·미등록 로봇은 명확히 표시하고, 임의 (0,0)이나 예시 좌표를 생성하지 않는다.

예상 변경 대상: 공통 참고 자세 설정과 읽기 도우미, ROS 실행기의 설정 읽기, server_page의 기존 응답, 웹의 최소 참고점 표시. 새 DB 테이블·새 주행 기능·웹 client 실행은 포함하지 않는다.

## 10. 검증 항목

- [ ] 초기 화면: 지도·로봇·히트맵·중요 경보가 구분되고 칸 번호/좌표가 기본 숨김.
- [ ] 1440×900, 1366×768, 좁은 화면에서 지도와 패널이 겹치지 않음. 좁은 화면에서는 사이드 패널을 접기/하단으로 이동.
- [ ] 동일한 좌표의 지도 기준점·로봇·히트맵·설비가 일치하고 y축이 뒤집히지 않음.
- [ ] 고정 시작값을 중복 입력하지 않고 읽음. 기본 시작값·실제 적용 설정·실측 현재 위치가 구분됨.
- [ ] pose_ok=false의 기본 (0,0)은 위치로 그리지 않음. pose_ok=true의 실제 (0,0)은 유효한 좌표로 처리함.
- [ ] 레이어 전환·새 표본 수신·사이드 패널 갱신으로 지도가 초기화되거나 확대가 풀리지 않음.
- [ ] 측정값 증가, 새 회차, 지도 변경, 회차 완료 시 표시 대상이 정확히 전환됨.
- [ ] 실제 DB 값과 상세/원본 칸 표시가 일치. 평균·중앙값·추정값을 혼동하지 않음.
- [ ] 벽 양쪽에 다른 값, 넓은 미측정 구역, 단일 측정점, 미검출, 위치 불확실 데이터로 보간 제한 확인.
- [ ] API 실패·연결 단절·오래된 데이터에서 마지막 갱신 시각과 미수신 상태 표시. 실패를 정상색으로 덮지 않음.
- [ ] ROS 모드에서는 기존 웹 client의 순찰·초기 위치 설정을 실행하지 않음.
- [ ] 로봇 상태/알림/사진이 실제 연결되지 않았다면 데이터 없음으로 보이고 성공으로 기록되지 않음.

원본 판정·DB 저장·주행 결과는 별도 검증 대상이다. 표시 검증은 가짜 데이터와 별도 시험 DB로 먼저 수행한다. 실제 로봇 이동을 포함하는 현장 검증은 운용 절차에 따라 별도로 한다.

기술 참고:

- [Leaflet: 비지리적 지도와 CRS.Simple](https://leafletjs.com/examples/crs-simple/crs-simple.html) — 이미지 오버레이·지도 단위·[y,x] 좌표의 공식 예시.

- [SciPy RegularGridInterpolator](https://docs.scipy.org/doc/scipy/reference/generated/scipy.interpolate.RegularGridInterpolator.html) — 규칙 격자의 선형 보간. 벽/신뢰도 마스크는 프로젝트에서 별도로 적용해야 함.
- [Canvas 투명도](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/globalAlpha) — 기반 지도를 가리지 않는 반투명 표현.

이 문서의 앞부분은 착수 당시 분석·제안이며, 아래 구현 결과와 구분한다. 실제 브라우저 검증·시험 PostgreSQL·격리된 가짜 ROS 메시지 연결은 완료했다. 운영 PC DB/DDS와 실제 로봇 수신·사진 이력 저장을 검증했다고 확대 해석하지 않는다.


## 12. 2026-10-15 구현 결과

- S1: HOME 기본값을 `scv_nav/config/robot_references.json`으로 옮겼다. 실행기와 웹이 같은 값을 읽으며 시작 파라미터 우선순위는 유지했다. 이미지 픽셀 해시·크기·해상도·원점 대조로 다른 지도에 참고점/구역을 적용하지 않는다.
- S2: `scv_monitor/ros_reader.py`가 상태·AMCL 갱신·실제 BatteryState·경보·설비 결과·Nav2 계획 경로를 구독한다. 서버가 ROS 모드에서만 시작한다. motion/action/service 클라이언트를 만들지 않는다. 사진은 제한된 캐시로 수신하고 선택 시 별도 인증된 GET으로만 내려준다.
- S3: 기존 평균 heat 응답은 호환용으로 유지하고, 웹용 중앙값/판정/신뢰도/미검출/출처를 readings에 추가했다. live 중앙값과 저장된 판정을 구분하고 회차 지도별 조회를 제공한다.
- S4: 지도 중심 화면·로봇 카드·선택 상세·최근 경보를 배치했다. 격자/번호/구역/시작 참고점/경로는 선택 표시다. 상태·히트맵·선택 갱신이 지도를 다시 만들지 않는다.
- S5: 연속 색상과 투명 Canvas 히트맵을 적용했다. 원본 칸 보기/농도 조절을 제공한다. 네 이웃의 유효성·신뢰도·벽 마스크를 확인한 경우에만 쌍선형 보간한다.
- S6: 결과 화면은 선택한 회차의 지도를 읽고 완료 후 반복 조회를 멈춘다. 설정은 지도/AP/설비 위주로 정리하고 내부 관리 항목을 접었다. 기준 지도 파일과 구역의 격자 간격을 서버에서 읽어 등록할 수 있다. 로봇 PC의 실제 지도 경로는 알 수 없으므로 자동으로 추측하지 않는다.
